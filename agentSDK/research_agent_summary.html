03  試験ポイント — このコードから読み取れる SDK の要点

配線そのものより、「なぜその引数・その順序でないと動かないのか」が問われる。 出典は本コードの実装と、インストール済み claude_agent_sdk 0.2.134 の types.py の定義・docstring。 ただし解答の枠組みは Exam Guide を優先する。 本コードは permission_mode="bypassPermissions" という例外的な設定を使っており、 実装の挙動をそのまま一般化すると出題意図から外れる箇所がある （下の Task / allowedTools のカードを参照）。 バージョンで既定値が変わる項目もあるため、出典の行番号を併記している。

ClaudeSDKClient は async with で開く
単発の query() と違い、ClaudeSDKClient は会話状態を保持する永続セッション。 async with を抜けた時点でセッションが閉じるため、対話ループは必ずこのブロックの内側に置く。
agent.py:132
description はルーティング用、権限は tools / disallowedTools
この 2 つを混同させるのが典型的な引っかけ。 description は親エージェントが「どれを呼ぶか」を判断する材料にすぎず、強制力はない。 report-writer の description にある「Does NOT conduct web searches」は制約ではなくルーティングのヒントで、 実際に検索できないのは tools に WebSearch を入れていないから。 「researcher の後に使う」といった順序や使いどころを書くのが description の役割。
agent.py:53-91 / types.py:87-105
tools はサブエージェントごとの権限境界
researcher は WebSearch, Write、data-analyst は Glob, Read, Bash, Write、 report-writer は Write, Glob, Read, Bash。 親の権限は継承されず、各サブエージェントは自分の tools に閉じる。 明示的に禁じたい場合は AgentDefinition.disallowedTools という拒否リストも別に存在する （このコードでは使っておらず、許可リストである tools だけで境界を作っている）。 役割分離＝ツール分離、という設計がそのまま出題される。

AgentDefinition は camelCase、ClaudeAgentOptions は snake_case
同じ概念でもクラスによって命名規約が違うので、そのまま書き写すと通らない。 AgentDefinition 側は disallowedTools / maxTurns / mcpServers / permissionMode / initialPrompt、 ClaudeAgentOptions 側は disallowed_tools / max_turns / mcp_servers / permission_mode。 なお AgentDefinition.model は "sonnet" などの別名のほか "inherit"（親と同じモデル）も受け付ける。
types.py:87-105 vs types.py:1766-1866
Task が allowedTools に無ければサブエージェントは起動しない
「サブエージェントが起動しない根本原因は？」への正解はこれ。 Task はサブエージェント起動の機構そのものであり、 コーディネーターがそれを呼ぶには allowedTools に "Task" が含まれている必要がある。 allowedTools から Task を外したコーディネーターは、 プロンプトにどれだけ委譲の意図を書いても手段を持たない。 プロンプトの書き方・description の不足・model の選択などはいずれも誤答の選択肢になる。
Exam Guide 1.3 / Purcell V2 3.1  |  agent.py:113
なぜそうなるか — permission_mode が効いている
機構としては tools が使えるツールの母集合、 allowed_tools は確認を出さずに自動実行するリスト、 disallowed_tools はコンテキストから除去して使用不可にする——という三者三様。 だが permission_mode が "default"（非対話セッションでは承認者がいない）や "dontAsk"（pre-approved でなければ拒否）である通常のケースでは、 「自動承認リストに無い」＝「実行されない」になる。 だから上のカードの結論が成り立つ。 例外は "bypassPermissions" で、これは明示的 deny を除き全て自動承認するため allowed_tools が事実上無効になる。 本コードがまさにその例外設定で、だからこそ確実に止めたい Skill は disallowed_tools 側に書く必要があった （組み込みスキルが数万トークンあり、読み込むと "Prompt is too long" になるため）。

フックはツールではない — モデルからは見えない
description との対比で問われる最重要点。 登録時にコールバックは "hook_0", "hook_1" …という文字列 ID に置き換えられ、 関数本体は Python 側の hook_callbacks 辞書に留まる。CLI に渡るのは {"matcher": null, "hookCallbackIds": ["hook_0"]} だけで、 関数名も docstring も型もシリアライズされない。 つまりモデルは「どのフックを呼ぶか」を判断しておらず、発火を決めるのは matcher（"Bash" や "Write|Edit" のようなツール名文字列、 None で全ツール）である。 AgentDefinition.description が「モデルに読ませる」ものなのに対し、フックは「ランタイムが機械的に発火させる」もの。

05  図だけでは読み取りにくい 3 点

帰属は共有変数ごしに決まる

フックは「どのサブエージェントの呼び出しか」を引数では受け取らない。 process_assistant_message() がメッセージごとに set_current_context() で _current_parent_id を書き換え、pre_tool_use_hook() がそれを読む——という 可変な共有状態が 2 モジュールをつないでいる。図の procMsg → setCtx と preHook の間に矢印はないが、実質ここが最も強い結合。

記録の入口は 2 つある

spawn の検知はメッセージストリーム側（process_assistant_message）、 個々のツール呼び出しはフック側（pre / post）。 SubagentTracker は両方から書き込まれる合流点で、 pre_tool_use_hook がメインエージェントの Task / Agent を スキップしているのは、この二重経路で同じ spawn を 2 回出さないため。

出力先は 3 系統に分かれている

コンソール＋transcript（write）、transcript のみ（write_to_file）、 機械可読な tool_calls.jsonl（_log_to_jsonl）。 _log_tool_use() はこの 3 つのうち上 2 つを使い分ける唯一の場所で、 transcript_writer が None のときだけ素の print に落ちる。
