## Domain 1: Agentic Architecture & Orchestration

### 1-1 自律タスク実行のためのエージェンティックループの設計・実装

**知識**
- ループのライフサイクル：リクエスト送信 → `stop_reason` を検査（`"tool_use"` か `"end_turn"` か）→ 要求されたツールを実行 → 結果を返して次のイテレーションへ。
- ツール結果は会話履歴に **追記** される。それによりモデルが次の行動を推論できる。
- モデル駆動の意思決定（文脈から次に呼ぶツールをClaudeが判断）と、事前に組んだ決定木・固定ツール順序との区別。

**スキル**
- `stop_reason == "tool_use"` で継続、`"end_turn"` で終了する制御フローを実装する。
- イテレーション間でツール結果をコンテキストに追加する。

**アンチパターン（引っかけ）**
- 自然言語のシグナルをパースして終了判定する
- 任意のイテレーション上限を **主たる** 停止機構にする
- assistant のテキスト有無を完了指標にする

---

### 1-2 Coordinator–Subagent パターンによるマルチエージェントのオーケストレーション

**知識**
- **Hub-and-spoke**：coordinator がサブエージェント間の通信・エラー処理・情報ルーティングを全て管理する。
- サブエージェントは **隔離されたコンテキスト** で動く。coordinator の会話履歴を自動継承しない。
- coordinator の役割：タスク分解、委譲、結果集約、クエリの複雑さに応じてどのサブエージェントを呼ぶかの判断。
- リスク：分解が細かすぎる／狭すぎると、広範な調査トピックのカバレッジが不完全になる。

**スキル**
- 常に全パイプラインを通すのではなく、要件を分析して **動的に** 呼ぶサブエージェントを選ぶ。
- 重複を最小化するようリサーチ範囲を分割（別々のサブトピック／ソース種別を割り当てる）。
- 反復的な refinement ループ：synthesis 出力のギャップを coordinator が評価 → 対象を絞ったクエリで search/analysis に再委譲 → カバレッジが十分になるまで synthesis を再実行。
- 可観測性・一貫したエラー処理・情報フロー制御のため、**全ての** サブエージェント通信を coordinator 経由にする。

---

### 1-3 サブエージェントの呼び出し、コンテキスト受け渡し、spawn の設定

**知識**
- **Task ツール** がサブエージェント spawn の機構。coordinator が呼ぶには `allowedTools` に `"Task"` を含める必要がある。
- サブエージェントのコンテキストは **プロンプトで明示的に渡す**。親コンテキストの自動継承も、呼び出し間のメモリ共有もない。
- **AgentDefinition** の設定内容：description、system prompt、サブエージェント種別ごとの tool 制限。
- **Fork ベースのセッション管理**：共通の分析ベースラインから分岐して異なるアプローチを探索する。

**スキル**
- 先行エージェントの成果を **完全な形で** サブエージェントのプロンプトに含める（web検索結果や文書分析結果を synthesis サブエージェントへ渡す等）。
- 構造化データ形式でコンテンツとメタデータ（source URL、文書名、ページ番号）を分離し、attribution を保持する。
- 並列 spawn は、**単一の coordinator レスポンス内で複数の Task ツール呼び出しを出す**（ターンを分けない）。
- coordinator プロンプトは手順の逐次指示ではなく、**リサーチ目標と品質基準** を指定してサブエージェントの適応性を確保する。

### 1-4 強制（enforcement）とハンドオフを伴うマルチステップワークフロー

**知識**
- **プログラム的強制（hooks, 前提条件ゲート）** と **プロンプトによる誘導** の違い。
- 決定論的な遵守が必要な場面（金融操作前の本人確認など）では、プロンプト指示だけでは **失敗率がゼロにならない**。
- 途中エスカレーション用の構造化ハンドオフ・プロトコル：顧客詳細、根本原因分析、推奨アクションを含む。

**スキル**
- 前提ステップ完了までダウンストリームのツール呼び出しをブロックする実装（`get_customer` が検証済み customer ID を返すまで `process_refund` をブロック）。
- 複数論点を含む顧客リクエストを個別項目に分解し、共有コンテキストで並列調査してから統一的な解決策を合成する。
- 会話ログにアクセスできない人間エージェントへエスカレーションする際、構造化サマリ（customer ID、根本原因、返金額、推奨アクション）を作成する。

### 1-5 Agent SDK hooks によるツール呼び出しのインターセプトとデータ正規化

**知識**
- `PostToolUse` 等の hook でツール **結果** をモデル処理前に変換する。
- 送信される **ツール呼び出し** をインターセプトしてコンプライアンス規則を強制する（閾値超の返金をブロック等）。
- hooks による決定論的保証 vs プロンプト指示による確率的遵守の区別。

**スキル**
- `PostToolUse` hook で異種データ形式（Unix timestamp、ISO 8601、数値ステータスコード）を正規化してからエージェントに渡す。
- ポリシー違反アクションをブロックし（$500超の返金など）、代替ワークフロー（人間へのエスカレーション）へリダイレクトする。
- ビジネスルールに **保証された遵守** が必要なら、プロンプトではなく hooks を選ぶ。

---

### 1-6 複雑なワークフローのタスク分解戦略

**知識**
- **固定的な逐次パイプライン（prompt chaining）** と **中間結果に応じた動的・適応的分解** の使い分け。
- prompt chaining の例：ファイル個別分析 → ファイル横断の統合パス。
- 各ステップの発見に応じてサブタスクを生成する適応的な調査プランの価値。

**スキル**
- 予測可能な多観点レビュー → prompt chaining／オープンエンドな調査 → 動的分解。
- 大規模コードレビューを「ファイル単位のローカル分析パス」＋「ファイル横断の統合パス」に分割し、**注意の希薄化（attention dilution）** を避ける。
- オープンエンドなタスク（レガシーコードへの網羅的テスト追加など）は、まず構造をマッピング → 高インパクト領域を特定 → 依存関係の発見に応じて適応する優先順位付きプランを作る。

### 1-7 セッション状態・再開・fork の管理

**知識**
- `--resume <session-name>` による名前付きセッションの再開。
- `fork_session`：共有の分析ベースラインから独立ブランチを作り、異なるアプローチを探索する。
- セッション再開時、**以前分析したファイルの変更をエージェントに伝える** ことの重要性。
- 古い（stale な）ツール結果を抱えて resume するより、**構造化サマリを与えて新セッションを開始する方が信頼性が高い**。

**スキル**
- 名前付きセッションで調査を継続する。
- `fork_session` で並列探索ブランチを作る（2つのテスト戦略／リファクタ案の比較など）。
- 再開（先行コンテキストが概ね有効）と新規開始＋サマリ注入（ツール結果が stale）の選択。
- 変更ファイルを伝えて **対象を絞った再分析** をさせる（全体の再探索を強いない）。

## Domain 2: Tool Design & MCP Integration

### 2-1 明確な description と境界を持つツールインターフェース設計

**知識**
- **ツールの description が、LLM のツール選択の主たる機構**。description が薄いと類似ツール間の選択が不安定になる。
- description に含めるべきもの：入力形式、クエリ例、エッジケース、境界の説明。
- 曖昧・重複した description は誤ルーティングを招く（`analyze_content` と `analyze_document` がほぼ同一など）。
- **system prompt の文言もツール選択に影響する**。キーワードに反応する指示が意図しないツール連想を作る。

**スキル**
- 各ツールの目的・入出力・「類似ツールではなくこれを使う条件」を明確に書き分ける。
- 機能重複を解消するためにリネーム＋description 更新（`analyze_content` → `extract_web_results`）。
- 汎用ツールを目的特化ツールに分割（`analyze_document` → `extract_data_points` / `summarize_content` / `verify_claim_against_source`）。
- よく書けた description を上書きしてしまうキーワード感応な system prompt を点検する。

---

### 2-2 MCP ツールの構造化エラーレスポンス

**知識**
- MCP の **`isError` フラグ** パターンでツール失敗をエージェントに伝える。
- エラー種別の区別：**transient**（タイムアウト、サービス停止）／**validation**（不正入力）／**business**（ポリシー違反）／**permission**。
- 一律のエラー応答（"Operation failed"）は、エージェントの適切な回復判断を妨げる。
- retryable / non-retryable の違い。構造化メタデータを返すことで無駄なリトライを防ぐ。

**スキル**
- `errorCategory`（transient/validation/permission）、`isRetryable` boolean、人間可読な説明を返す。
- ビジネスルール違反には `retriable: false` と顧客向けの説明を含め、エージェントが適切に伝えられるようにする。
- サブエージェント内で transient 失敗をローカル回復し、ローカルで解決できないものだけを **部分結果と試行内容を添えて** coordinator に伝播する。
- **アクセス失敗（リトライ判断が必要）** と **有効な空結果（成功したが該当なし）** を区別する。

---

### 2-3 エージェント間のツール配分と tool_choice の設定

**知識**
- ツールを与えすぎる（4–5個で足りるところに18個）と、判断の複雑さが増して **ツール選択の信頼性が落ちる**。
- 専門外のツールを持つエージェントは誤用しがち（synthesis エージェントが web検索を試みる等）。
- **スコープ付きツールアクセス**：役割に必要なツールだけを与え、高頻度な特定ニーズに限り限定的な役割横断ツールを持たせる。
- `tool_choice` の3種：`"auto"` / `"any"` / 特定ツール強制 `{"type": "tool", "name": "..."}`。

**スキル**
- 各サブエージェントのツールセットを役割相当に制限し、専門外の誤用を防ぐ。
- 汎用ツールを制約付き代替に置換（`fetch_url` → 文書URLを検証する `load_document`）。
- 高頻度ニーズにはスコープ付き役割横断ツールを与えつつ（synthesis 用の `verify_fact` 等）、複雑ケースは coordinator 経由にする。
- 強制選択で特定ツールを先に呼ばせる（enrichment 前に `extract_metadata`）→ 後続は次ターンで処理。
- `tool_choice: "any"` で会話テキストではなく必ずツールを呼ばせる。

---

### 2-4 MCP サーバの Claude Code / エージェントワークフローへの統合

**知識**
- **スコープ**：プロジェクトレベル `.mcp.json`（チーム共有ツール）vs ユーザレベル `~/.claude.json`（個人・実験用）。
- `.mcp.json` での **環境変数展開**（`${GITHUB_TOKEN}`）による、シークレットをコミットしない資格情報管理。
- 設定済みの全 MCP サーバのツールは **接続時に discovery され、同時に利用可能** になる。
- **MCP resources**：コンテンツカタログ（issue サマリ、ドキュメント階層、DBスキーマ）を公開し、探索的なツール呼び出しを減らす機構。

**スキル**
- 共有 MCP サーバをプロジェクトスコープ `.mcp.json` に、環境変数展開付きで設定する。
- 個人・実験用はユーザスコープ `~/.claude.json` に設定する。
- MCP ツールの description を詳細に書き、エージェントが組み込みツール（Grep 等）をより高機能な MCP ツールより優先してしまうのを防ぐ。
- 標準的な連携（Jira 等）は **既存のコミュニティ MCP サーバを選ぶ**。カスタム実装はチーム固有ワークフロー用に留める。
- コンテンツカタログを MCP resources として公開し、探索的ツール呼び出しなしに利用可能データを可視化する。

---

### 2-5 組み込みツール（Read, Write, Edit, Bash, Grep, Glob）の選択と活用

**知識**
- **Grep** = 内容検索（関数名、エラーメッセージ、import 文などのパターン）。
- **Glob** = ファイルパスのパターンマッチ（名前・拡張子でファイルを探す）。
- **Read/Write** = ファイル全体の操作。**Edit** = 一意なテキストマッチによるピンポイント修正。
- Edit がテキストの一意性不足で失敗したら、**Read + Write** をフォールバックにする。

**スキル**
- コードベース横断の内容検索には Grep（関数の呼び出し元探索、エラーメッセージ特定）。
- 命名パターンでのファイル探索には Glob（`**/*.test.tsx`）。
- 一意なアンカーテキストが見つからない場合は Read → Write。
- 全ファイルを先に読むのではなく、**Grep でエントリポイントを見つけ、Read で import を辿ってフローを追う** 漸進的な理解の構築。
- ラッパーモジュール越しの関数利用追跡：まず全 export 名を特定し、次に各名前をコードベース横断で検索する。

## Domain 3: Claude Code Configuration & Workflows

### 3-1 CLAUDE.md の階層・スコープ・モジュール構成

**知識**
- 階層：**ユーザレベル** `~/.claude/CLAUDE.md` / **プロジェクトレベル** `.claude/CLAUDE.md` またはルート `CLAUDE.md` / **ディレクトリレベル**（サブディレクトリの CLAUDE.md）。
- ユーザレベル設定はそのユーザにしか効かない。**バージョン管理でチームに共有されない**。
- **`@import` 構文** で外部ファイルを参照し、CLAUDE.md をモジュール化する。
- **`.claude/rules/`** ディレクトリ：モノリシックな CLAUDE.md の代替として、トピック別ルールファイルを整理する。

**スキル**
- 階層起因の不具合診断（新メンバーに指示が届かない＝プロジェクトレベルでなくユーザレベルに書かれている）。
- `@import` で各パッケージの CLAUDE.md に関連する標準ファイルだけを選択的に含める。
- 巨大な CLAUDE.md を `.claude/rules/` のトピック別ファイル（testing.md、api-conventions.md、deployment.md）に分割する。
- **`/memory` コマンド** でどのメモリファイルがロードされているかを検証し、セッション間の挙動不一致を診断する。

---

### 3-2 カスタムスラッシュコマンドと Skills の作成・設定

**知識**
- **プロジェクトスコープ** `.claude/commands/`（バージョン管理で共有）vs **ユーザスコープ** `~/.claude/commands/`（個人）。
- Skills は `.claude/skills/` に **SKILL.md** を置く。frontmatter で `context: fork`、`allowed-tools`、`argument-hint` を設定できる。
- **`context: fork`**：skill を隔離されたサブエージェントコンテキストで実行し、skill の出力がメイン会話を汚染するのを防ぐ。
- 個人用カスタマイズ：`~/.claude/skills/` に **別名で** 個人版を作り、チームメイトに影響を与えない。

**スキル**
- チーム全体で使うスラッシュコマンドは `.claude/commands/` に置く。
- 冗長な出力を出す skill（コードベース分析）や探索的な skill（代替案のブレスト）は `context: fork` で隔離する。
- `allowed-tools` で skill 実行中のツールアクセスを制限する（ファイル書き込みのみに限定して破壊的操作を防ぐ等）。
- `argument-hint` で、引数なし実行時に必要パラメータを開発者に促す。
- **Skills（オンデマンド・タスク特化）** と **CLAUDE.md（常時ロード・普遍的な標準）** を使い分ける。

---

### 3-3 パス指定ルールによる条件付き規約ロード

**知識**
- `.claude/rules/` のファイルに **YAML frontmatter の `paths` フィールド**（glob パターン）を書くと、条件付きでルールが有効化される。
- パススコープのルールは **該当ファイルを編集するときだけロード** されるため、無関係なコンテキストとトークン消費を減らせる。
- 複数ディレクトリにまたがる規約には、ディレクトリレベルの CLAUDE.md より **glob パターンのルールが有利**（テストファイルがコードベース全体に散在する場合など）。

**スキル**
- `paths: ["terraform/**/*"]` のようなパススコープ付きルールファイルを作る。
- ディレクトリ位置によらずファイル種別で規約を適用する（`**/*.test.tsx`）。
- 規約がコードベース全体に散らばるファイルに適用される場合、サブディレクトリ CLAUDE.md ではなくパス指定ルールを選ぶ。

---

### 3-4 Plan mode と直接実行の判断

**知識**
- **Plan mode** は、大規模変更・複数の妥当なアプローチ・アーキテクチャ判断・複数ファイル修正を伴う複雑タスク向け。
- **直接実行** は、単純でスコープが明確な変更向け（1関数に検証を1つ足す等）。
- Plan mode により、変更をコミットする前に安全にコードベースを探索・設計でき、高コストな手戻りを防げる。
- **Explore サブエージェント**：冗長な discovery 出力を隔離し、サマリだけを返してメイン会話のコンテキストを保つ。

**スキル**
- アーキテクチャ影響のあるタスクには plan mode（マイクロサービス再構成、45ファイル以上に及ぶライブラリ移行、インフラ要件の異なる統合方式の選択）。
- スコープが明確で理解済みの変更には直接実行（スタックトレースの明確な単一ファイルのバグ修正、日付検証の条件追加）。
- 多段階タスクでのコンテキスト枯渇を防ぐため、冗長な discovery フェーズに Explore サブエージェントを使う。
- **調査は plan mode、実装は直接実行** という組み合わせ。

---

### 3-5 段階的改善のための反復リファインメント手法

**知識**
- 散文の説明が一貫して解釈されないとき、**具体的な入出力の例** が期待する変換を伝える最も効果的な手段。
- **テスト駆動の反復**：先にテストスイートを書き、テスト失敗を共有しながら段階的に改善する。
- **Interview パターン**：実装前に Claude に質問させ、開発者が想定していなかった論点を表面化させる。
- 複数の問題を **1つのメッセージにまとめる**（相互作用する問題）か、**逐次修正する**（独立した問題）かの判断。

**スキル**
- 自然言語の説明で結果がぶれるとき、具体的な入出力例を **2–3個** 提示する。
- 期待挙動・エッジケース・性能要件をカバーするテストを実装前に書き、失敗を共有して反復する。
- 不慣れな領域では interview パターンで設計論点（キャッシュ無効化戦略、失敗モード）を先に洗い出す。
- エッジケース修正には、入力例と期待出力を伴う具体的なテストケースを与える（マイグレーションスクリプトの null 値など）。
- 修正が相互作用する場合は1つの詳細メッセージにまとめ、独立している場合は逐次反復する。

---

### 3-6 Claude Code の CI/CD パイプライン統合

**知識**
- **`-p`（`--print`）フラグ**：自動化パイプラインでの非対話モード実行。
- **`--output-format json`** と **`--json-schema`** CLI フラグで CI 上の構造化出力を強制する。
- **CLAUDE.md** が、CI から起動された Claude Code にプロジェクト文脈（テスト標準、fixture 規約、レビュー基準）を渡す機構。
- **セッションコンテキストの隔離**：コードを生成したのと同じセッションは、自分の変更をレビューするのに独立インスタンスより不得手。

**スキル**
- CI では `-p` を付けて対話入力待ちのハングを防ぐ。
- `--output-format json` ＋ `--json-schema` で機械可読な findings を作り、インラインPRコメントとして自動投稿する。
- 新規コミット後の再レビューでは **過去の findings をコンテキストに含め**、新規または未対応の問題のみ報告させて重複コメントを防ぐ。
- 既存テストファイルをコンテキストに与え、テスト生成が既存カバー済みシナリオの重複提案をしないようにする。
- テスト標準・価値あるテストの基準・利用可能な fixture を CLAUDE.md に文書化し、低価値なテスト出力を減らす。

## Domain 4: Prompt Engineering & Structured Output

### 4-1 明確な判定基準で精度を上げ、偽陽性を減らすプロンプト設計

**知識**
- 曖昧な指示より **明示的な基準**（「コメントが主張する挙動が実際のコード挙動と矛盾する場合にのみ flag」vs「コメントが正確か確認して」）。
- `"be conservative"` / `"only report high-confidence findings"` のような一般的指示は、**具体的なカテゴリ基準に比べて精度改善に寄与しない**。
- **偽陽性は伝染する**：偽陽性率の高いカテゴリは、**正確なカテゴリへの信頼まで損なう**。

**スキル**
- 信頼度ベースのフィルタリングではなく、**報告する種類（bugs, security）とスキップする種類（軽微な style、ローカル慣習）** を定義した具体的なレビュー基準を書く。
- 偽陽性の高いカテゴリを **一時的に無効化** して開発者の信頼を回復させ、その裏でそのカテゴリのプロンプトを改善する。
- 各 severity レベルに **具体的なコード例** を紐づけた明示的な severity 基準を定義し、分類を一貫させる。

**引っかけパターン**
- 強調の増幅（"be very, very conservative"）／モデル自己申告 confidence でのソート・平均・多数決／リネームのみ／人間に我慢を求める／代理指標（severity ≒ 行数）／レビュー対象を減らす

---

### 4-2 Few-shot prompting による出力の一貫性・品質向上

**知識**
- 詳細な指示だけでは出力が不安定なとき、**few-shot 例が最も効果的**（一貫した書式で actionable な出力を得る手段）。
- 曖昧ケースの扱いを示す役割（曖昧なリクエストでのツール選択、branch レベルのテストカバレッジ欠落など）。
- few-shot により、事前指定したケースへのマッチだけでなく、**新規パターンへ判断を一般化** できる。
- 抽出タスクでの **ハルシネーション低減** に有効（非公式な計量表現、多様な文書構造の扱い）。

**スキル**
- 曖昧シナリオ向けに **2–4個** の的を絞った few-shot 例を作り、「なぜ他の妥当な選択肢ではなくこれを選んだか」の推論を示す。
- 望ましい出力書式（location, issue, severity, suggested fix）を実演する例を含める。
- 許容されるコードパターンと本物の問題を区別する例で、偽陽性を減らしつつ一般化を可能にする。
- 多様な文書構造（インライン引用 vs 参考文献リスト、methodology セクション vs 本文埋め込み）の正しい扱いを実演する。
- 必須フィールドが空/null で抽出される問題に対し、多様な形式の文書からの正しい抽出例を追加する。

**引っかけパターン**
- 例を大量に入れる（コンテキストを膨張させ、重要な例のシグナルを希釈する）／「明示的基準の代わりに」few-shot を使う（補完関係であって代替ではない）／コードレビューは few-shot の対象外、という主張（誤り）

---

### 4-3 Tool use と JSON Schema による構造化出力の強制

**知識**
- **`tool_use` ＋ JSON Schema がスキーマ準拠出力の最も信頼できる手段**。JSON 構文エラーを構造的に排除する。
- `tool_choice` の区別：
  - `"auto"` … ツールを呼ばずテキストを返す可能性がある
  - `"any"` … **必ず**ツールを呼ぶが、どれを呼ぶかはモデルが選ぶ
  - 強制選択 … 指定した名前のツールを必ず呼ぶ
- 厳密な JSON Schema は **構文エラーは消せるが、意味的エラーは防げない**（明細合計が総額と一致しない、値が誤ったフィールドに入る等）。
- スキーマ設計：required vs optional、拡張可能なカテゴリのための **enum + `"other"` + 詳細文字列** パターン。

**スキル**
- 抽出用ツールを JSON Schema を入力パラメータとして定義し、`tool_use` レスポンスから構造化データを取り出す。
- 複数の抽出スキーマがあり文書種別が不明な場合、`tool_choice: "any"` で構造化出力を保証する。
- `tool_choice: {"type": "tool", "name": "extract_metadata"}` で、enrichment の前に特定抽出を確実に走らせる。
- ソース文書に情報が無い可能性があるフィールドは **optional（nullable）** にし、required を満たすためのモデルの値捏造を防ぐ。
- 曖昧ケース用に `"unclear"`、拡張カテゴリ用に `"other"` + 詳細フィールドを enum に追加する。
- 一貫しないソース書式に対応するため、厳密なスキーマと併せて **書式正規化ルールをプロンプトに含める**。

---

### 4-4 抽出品質のための検証・リトライ・フィードバックループ

**知識**
- **Retry-with-error-feedback**：リトライ時に具体的な検証エラーをプロンプトに付加して、修正方向へ導く。
- **リトライの限界**：必要な情報がソース文書に **そもそも存在しない** 場合、リトライは無効（書式・構造エラーとは異なる）。
- フィードバックループ設計：どのコード構造が findings を誘発したかを **`detected_pattern` フィールド** で追跡し、却下パターンを体系的に分析する。
- **意味的検証エラー**（合計が合わない、フィールド配置ミス）と **スキーマ構文エラー**（tool use で排除済み）の違い。

**スキル**
- 後続リクエストに **元の文書＋失敗した抽出結果＋具体的な検証エラー** を含めて自己修正させる。
- リトライが無効なケース（情報が未提供の外部文書にしか存在しない）と有効なケース（書式不一致、構造的な出力エラー）を見分ける。
- findings に `detected_pattern` を付け、開発者が却下したときの偽陽性パターン分析を可能にする。
- 自己検証フローの設計：`calculated_total` を `stated_total` と併せて抽出して不一致を flag する、ソースデータの矛盾に `conflict_detected` boolean を付ける。

---

### 4-5 効率的なバッチ処理戦略

**知識**
- **Message Batches API**：コスト **50% 削減**、最大 **24時間** の処理ウィンドウ、**レイテンシSLAの保証なし**。
- 適合：非ブロッキングでレイテンシ許容のワークロード（夜間レポート、週次監査、夜間テスト生成）。
- 不適合：ブロッキングなワークフロー（pre-merge チェック）。
- バッチAPIは **単一リクエスト内のマルチターン tool calling を非サポート**（リクエスト途中でツールを実行して結果を返せない）。
- **`custom_id`** でリクエスト／レスポンスの対応付けを行う。

**スキル**
- レイテンシ要件に応じたAPI選択：ブロッキングな pre-merge チェックは同期API、夜間・週次分析はバッチAPI。
- SLA制約からバッチ投入頻度を計算する（24時間の処理を前提に30時間SLAを保証するには4時間ごとの投入ウィンドウ）。
- バッチ失敗の処理：`custom_id` で特定した **失敗分のみ** を、適切な修正（コンテキスト長超過分のチャンク化）を加えて再投入する。
- 大量処理の前にサンプルセットでプロンプトを磨き、初回成功率を上げて再投入コストを減らす。

**判断順序（重要）**
1. ブロッキングか？→ ブロッキングならバッチ不可（確定）
2. 非ブロッキングなら SLA 計算 → SLAが24時間未満ならバッチは構造的に不可能

---

### 4-6 マルチインスタンス／マルチパスのレビューアーキテクチャ

**知識**
- **自己レビューの限界**：モデルは生成時の推論文脈を保持しているため、同一セッション内では自分の判断を疑いにくい。
- 先行推論文脈を持たない **独立したレビューインスタンス** の方が、自己レビュー指示や extended thinking より微細な問題を捕捉できる。
- **マルチパスレビュー**：大規模レビューをファイル単位のローカル分析パス＋ファイル横断の統合パスに分け、注意の希薄化と矛盾した findings を避ける。

**スキル**
- 2つ目の独立した Claude インスタンスで、生成側の推論文脈なしにコードをレビューさせる。
- 大規模な複数ファイルレビューを、ローカル問題向けのファイル単位パスと、ファイル横断のデータフロー分析用の統合パスに分割する。
- 各 finding にモデル自身の confidence を併記させる検証パスを走らせ、キャリブレーションされたレビュールーティングを可能にする。

---

## Domain 5: Context Management & Reliability

### 5-1 長い対話を通じた重要情報の保持

**知識**
- **漸進的要約のリスク**：数値、パーセンテージ、日付、顧客が述べた期待などが曖昧な要約に潰される。
- **"lost in the middle" 効果**：モデルは長い入力の **先頭と末尾** は確実に処理するが、**中間部分** の findings を落とすことがある。
- ツール結果はコンテキストに蓄積し、関連度に不釣り合いなトークンを消費する（注文照会で40以上のフィールドが返るが必要なのは5個）。
- 後続APIリクエストで **完全な会話履歴を渡す** ことの重要性（対話の一貫性維持）。

**スキル**
- 取引に関する事実（金額、日付、注文番号、ステータス）を抽出し、要約された履歴の **外側** に置く永続的な "case facts" ブロックとして毎プロンプトに含める。
- 複数論点セッションでは、構造化された issue データ（order ID、金額、ステータス）を別のコンテキストレイヤに永続化する。
- 冗長なツール出力を、蓄積される前に必要フィールドだけへ削る。
- 集約入力では **主要 findings のサマリを先頭に置き**、詳細は明示的なセクション見出しで整理して位置効果を緩和する。
- サブエージェントに、構造化出力へメタデータ（日付、ソース位置、方法論的文脈）を含めさせ、下流の合成精度を担保する。
- 下流エージェントのコンテキスト予算が限られる場合、上流エージェントに冗長な本文・推論チェーンではなく **構造化データ（key facts、citations、relevance scores）** を返させる。

---

### 5-2 エスカレーションと曖昧性解決のパターン

**知識**
- 適切なエスカレーション条件：**顧客が人間を要求した / ポリシーの例外・空白（単に「複雑」なだけではない） / 意味のある進展ができない**。
- 顧客が明示的に人間を要求したら **即座にエスカレーション**。問題が単純なら解決を提案する、との区別。
- **感情ベースのエスカレーションやモデルの自己申告 confidence スコアは、実際のケース複雑度の代理指標として信頼できない**。
- 顧客の候補が複数ヒットした場合、ヒューリスティックで選ばず **追加識別子を求めて確認する**。

**スキル**
- 明示的なエスカレーション基準を、いつエスカレーションし、いつ自律解決するかを示す few-shot 例とともに system prompt に加える。
- 顧客が人間エージェントを明示要求したら、まず調査を試みずに即応じる。
- 対応可能な範囲なら不満を受け止めつつ解決を提案し、**顧客が再度希望を述べた場合にのみ** エスカレーションする。
- ポリシーが顧客の具体的な要求に対して曖昧・沈黙している場合はエスカレーションする（自社サイトの価格調整しか規定していないのに競合価格マッチを求められた等）。
- ツール結果が複数マッチを返したら、追加識別子を求めるようエージェントに指示する。

---

### 5-3 マルチエージェント系におけるエラー伝播戦略

**知識**
- **構造化エラーコンテキスト**（失敗の種類、試みたクエリ、部分結果、代替アプローチ）が、coordinator の賢い回復判断を可能にする。
- **アクセス失敗**（タイムアウト＝リトライ判断が必要）と **有効な空結果**（成功したが該当なし）の区別。
- 汎用的なエラーステータス（"search unavailable"）は、coordinator にとって価値ある文脈を隠してしまう。
- **どちらもアンチパターン**：エラーを黙って握り潰す（空結果を成功として返す）／単一失敗でワークフロー全体を終了させる。

**スキル**
- 失敗種別・試行内容・部分結果・代替候補を含む構造化エラーコンテキストを返す。
- アクセス失敗と有効な空結果をエラー報告上で区別する。
- サブエージェントは transient 失敗をローカル回復し、解決できないものだけを試行内容・部分結果とともに伝播する。
- synthesis 出力に **カバレッジ注記** を付け、十分な裏付けのある findings と、ソース不可用でギャップのある領域を示す。

---

### 5-4 大規模コードベース探索でのコンテキスト管理

**知識**
- **長時間セッションでのコンテキスト劣化**：回答が一貫しなくなり、以前発見した具体的なクラスではなく「典型的なパターン」を参照し始める。
- **scratchpad ファイル** の役割：コンテキスト境界を越えて重要な発見を永続化する。
- サブエージェント委譲により、冗長な探索出力を隔離しつつ、メインエージェントは高レベルの理解を統括する。
- クラッシュ復旧のための構造化状態永続化：各エージェントが既知の場所へ状態をエクスポートし、coordinator が再開時に manifest を読み込む。

**スキル**
- 具体的な問い（「全テストファイルを探す」「返金フローの依存を追跡する」）をサブエージェントに投げ、メインエージェントは高レベル調整を保持する。
- エージェントに scratchpad ファイルで重要な発見を記録させ、後続の問いでそれを参照させてコンテキスト劣化に対抗する。
- あるフェーズの発見を要約してから次フェーズのサブエージェントを spawn し、サマリを初期コンテキストに注入する。
- 構造化されたエージェント状態エクスポート（manifest）でクラッシュ復旧を設計し、coordinator が再開時に読み込んでエージェントプロンプトに注入する。
- 冗長な discovery 出力でコンテキストが埋まる長時間セッションでは **`/compact`** を使う。

---

### 5-5 人間レビューのワークフロー設計と confidence キャリブレーション

**知識**
- **総合精度（97%等）は、特定の文書種別やフィールドでの低性能を覆い隠す** リスクがある。
- **層化ランダムサンプリング（stratified random sampling）** で、高 confidence 抽出のエラー率を測定し、新種のエラーパターンを検出する。
- **フィールド単位の confidence スコア** を、ラベル付き検証セットでキャリブレーションしてレビューの注意を振り分ける。
- 高 confidence 抽出を自動化する前に、**文書種別・フィールドのセグメント別に精度を検証** することの重要性。

**スキル**
- 高 confidence 抽出の層化ランダムサンプリングを実装し、継続的なエラー率測定と新規パターン検出を行う。
- 人間レビューを減らす前に、文書種別・フィールドごとの精度を分析し、全セグメントで一貫していることを確認する。
- モデルにフィールド単位の confidence を出力させ、ラベル付き検証セットでレビュー閾値をキャリブレーションする。
- モデルの confidence が低い抽出、またはソース文書が曖昧・矛盾している抽出を人間レビューへ回し、限られたレビュー能力を優先配分する。

---

### 5-6 マルチソース合成における出所（provenance）の保持と不確実性の扱い

**知識**
- 要約ステップで **claim–source の対応を保持せずに** 圧縮すると、ソース帰属が失われる。
- 構造化された **claim-source mapping** を synthesis エージェントが保持・マージすることの重要性。
- 信頼できる複数ソース間で統計値が矛盾する場合、**恣意的に1つを選ばず、ソース帰属付きで矛盾を注記する**。
- **時系列データ**：出版日・収集日を構造化出力に必須とし、時点の違いが矛盾と誤解されるのを防ぐ。

**スキル**
- サブエージェントに構造化された claim-source mapping（source URL、文書名、該当抜粋）を出力させ、下流が synthesis を通じて保持する。
- 確立された findings と係争中の findings を明示的なセクションで区別し、元のソースの表現と方法論的文脈を保持したレポート構成にする。
- 矛盾する値を含めたまま明示的に注記して文書分析を完了し、synthesis に渡す前に coordinator に調停を判断させる。
- サブエージェントに出版日・データ収集日を構造化出力へ含めさせ、正しい時間的解釈を可能にする。
- 合成出力ではコンテンツ種別に応じた表現をする（財務データは表、ニュースは散文、技術的findingsは構造化リスト）。**全てを一律の形式に変換しない**。

---

## 横断的に効く判断原則（試験対策メモ）

1. **決定論が必要なら hooks / プログラム的ゲート。プロンプトは確率的**（1-4, 1-5）
2. **能力は設定で決まる**（tool 制限、`allowedTools`、`allowed-tools`）。プロンプトでの禁止は保証にならない（1-3, 2-3, 3-2）
3. **サブエージェントは明示的に渡したものしか見えない**（1-2, 1-3, 5-1）
